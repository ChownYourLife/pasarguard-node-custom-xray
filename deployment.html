Deploy the custom PasarGuard node image

How to replace the image on an existing PasarGuard Node Docker Compose server, verify it with a canary, and roll back without touching credentials, certificates, or data.

Canary first. Do not roll out to every node at once. Recreating the Node container interrupts its Xray processes and disconnects active clients on that node. Validate one non-critical server, then move one server at a time.

Production image reference: use this exact digest ghcr.io/chownyourlife/pasarguard-node-custom-xray@sha256:bb09c94de5c448c1397634808f4158166a83ad1df80b0c180183d3cedf815f3f

Existing server: changing the image alone is not enough if the host used the installer's core-update flow. That flow sets XRAY_EXECUTABLE_PATH to an external core under the data directory. Set XRAY_EXECUTABLE_PATH=/usr/local/bin/xray in the actual environment, and keep the node data mount (default /var/lib/pg-node). See deploy step 3.

Scope and image

This guide is for an existing PasarGuard Node deployment already managed by Docker Compose. The deployment procedure changes the service image and sets or confirms XRAY_EXECUTABLE_PATH=/usr/local/bin/xray in the environment Compose uses, so Node does not keep selecting an external core. Those are the intended changes; an obsolete host-binary override may also have to be removed. The procedure does not create a node, issue certificates, rotate an API key, or change panel records.

Instructions, not executed commands. The deployment, verification, and rollback commands on this page are for you to run on your own server. They were not run against your server for this project. The checks that were executed are listed separately in Verification evidence.

Before touching a server

  • Check panel compatibility first. The Node v0.5.5 release notes explicitly list panel versions v5.4.1 and v5.5.0 as compatible. Older panels are unverified by this project. Routing hot reload and Xray WireGuard inbounds require panel v5.5.0 according to those release notes. Do not combine a panel upgrade with this node-image canary.
  • Preserve credentials, certificates, and data. Existing API_KEY, TLS certificate/key files, data under the existing node data directory (default /var/lib/pg-node), network mode, capabilities, and all other environment variables must remain unchanged. The one environment value that must be set or confirmed is XRAY_EXECUTABLE_PATH=/usr/local/bin/xray, because the upstream core-update flow can point it at an external core (see step 3 below). The image does not rotate or regenerate credentials or certificates. The API key in the panel must still match the node environment.
  • Do not newly enable WireGuard capabilities or routing. Keep the host's existing cap_add, sysctls, and routing configuration exactly as they are. This image supplies a core binary; it does not configure host networking features.
  • Expect disruption. Recreating the Node container stops its managed Xray process and disconnects sessions through that node. Schedule a maintenance window and pick a low-risk server for the canary.
  • Check the host architecture. Only linux/amd64 and linux/arm64 are published. Check with uname -m: x86_64 maps to amd64, aarch64 or arm64 maps to arm64.
  • Check Docker and egress. Use a current Docker Engine with the Compose v2 plugin, confirm the daemon is reachable, and allow HTTPS access to ghcr.io for the pull.
uname -m
docker compose version
docker info >/dev/null

The last command prints nothing when the Docker daemon is reachable. If it fails, fix Docker access before changing any Compose file.

Deploy to an existing server

Find the directory of the stack that is already running; do not deploy from a path you merely guessed. The installer's conventional paths are mentioned below only as recognizable defaults, not as universal deployment paths.

1Locate the live stack and the actual service name

# List running Compose projects and their status.
docker compose ls

# On newer Compose versions, this includes the config file path(s).
docker compose ls --format json

If --format json is unavailable, identify the Node container from docker ps, then read only its Compose labels (not the full container environment):

# Compose project name, working directory, and config file path(s).
docker inspect --format '{{index .Config.Labels "com.docker.compose.project"}}' CONTAINER_ID
docker inspect --format '{{index .Config.Labels "com.docker.compose.project.working_dir"}}' CONTAINER_ID
docker inspect --format '{{index .Config.Labels "com.docker.compose.project.config_files"}}' CONTAINER_ID

Replace CONTAINER_ID with the actual container ID. If the stack is started by a wrapper or systemd unit with explicit -f file arguments, use that same invocation and working directory.

Keep the existing Compose project; do not create a second stack. The upstream installer conventionally uses project name pg-node (matching the /opt/pg-node directory basename), /opt/pg-node/docker-compose.yml, and /opt/pg-node/.env. A custom --name or APP_DIR changes those names or paths, so treat the defaults as conventional, not universal. Either stay in the existing stack directory or apply the same -p project and -f file options (or exported COMPOSE_PROJECT_NAME/COMPOSE_FILE) to every Compose command. Running from a different directory without them can create a new project with a separate container.

Change to the stack directory and confirm the service names:

docker compose config --services

The upstream default service name is node, and the examples below use it. Use the actual service name reported by your stack. Substitute it in SERVICE; do not blindly assume node if your Compose project names it differently.

SERVICE=node   # replace with the actual service name if different

All remaining docker compose commands assume you are working in this existing stack context. If you are not, include the same -p and -f options on every command.

2Record the current image and back up the real Compose file

Record the current image reference and image ID for rollback. These commands deliberately print only selected fields; they do not dump the container's full environment, which can contain the API key.

STAMP=$(date -u +%Y%m%dT%H%M%SZ)
CID=$(docker compose ps -q "$SERVICE")

# Current image reference, tag, and image ID.
docker compose images "$SERVICE"
docker inspect --format 'container={{.Id}} image_ref={{.Config.Image}} image_id={{.Image}}' "$CID"

# Preserve the exact previous image locally under a rollback tag.
docker tag "$(docker inspect --format '{{.Image}}' "$CID")" "pg-node-rollback:$STAMP"

If the service has more than one container, capture each container separately before proceeding. A normal single-server node service should have one.

Back up the file that Compose actually reads. The example uses compose.yaml; substitute the real filename from the ConfigFiles output, such as docker-compose.yml.

COMPOSE_PATH=compose.yaml   # replace with the actual Compose file
cp -p -- "$COMPOSE_PATH" "$COMPOSE_PATH.bak.$STAMP"

If there are multiple Compose files, back up each one. If an env file supplies the service environment (the upstream installer convention is /opt/pg-node/.env; custom APP_DIR values differ), back it up as well before changing XRAY_EXECUTABLE_PATH:

ENV_FILE=.env   # only if the service uses an env file; use its actual path
cp -p -- "$ENV_FILE" "$ENV_FILE.bak.$STAMP"

The env backup contains the API key and possibly other sensitive values. Restrict its permissions, keep it out of the repository and chat, and never paste it into a ticket. Keep the image-reference record separate from the env backup.

STAMP, CID, COMPOSE_PATH, and ENV_FILE are shell variables. Keep the same shell session for the deployment and rollback, or record their values in your private notes so you can restore the same files later.

3Point Xray at the baked binary and remove host overrides

This is a required companion change, not just an image swap. The upstream PasarGuard installer script (read for this guide, not executed) has a core-update flow that writes XRAY_EXECUTABLE_PATH into the env file, pointing at an external core under the data directory (DATA_DIR/xray-core/xray). If that setting is carried forward, Node keeps using the external core after the image changes, and the custom binary at /usr/local/bin/xray is ignored.

In the environment actually used by the service, set exactly:

XRAY_EXECUTABLE_PATH=/usr/local/bin/xray

If the service uses env_file, change the value in that file (upstream installer convention: /opt/pg-node/.env; custom paths differ). If the value is written inline in the Compose service's environment, change it there. If a systemd unit, wrapper, or docker run command injects the variable, change it in that file or invocation as well, and ensure there is only one effective value. Add the line if it is missing; change only this value. Preserve API_KEY, certificate paths, data paths, network settings, capabilities, and all other variables.

# Current value in the running container; this filters to one variable only.
docker inspect --format '{{range .Config.Env}}{{println .}}{{end}}' "$CID" | grep '^XRAY_EXECUTABLE_PATH=' || true

# If ENV_FILE was set for an env file, check that actual file.
grep -nE '^[[:space:]]*XRAY_EXECUTABLE_PATH[[:space:]]*=' "$ENV_FILE" || true

# Supplemental: check inline environment in the rendered Compose config.
docker compose config | grep -nE 'XRAY_EXECUTABLE_PATH|/usr/local/bin/xray' || true

# A bind mount at /usr/local/bin/xray would also hide the baked binary.
docker inspect --format '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}' "$CID" | grep -F '/usr/local/bin/xray' || true
  • Required value: XRAY_EXECUTABLE_PATH=/usr/local/bin/xray. Do not leave it pointing at <data-dir>/xray-core/xray.
  • Host bind mount at the binary path: remove only that binary mount after the backup. Do not remove the data mount.
  • Custom entrypoint or wrapper: if it launches a host core, resolve that override separately; do not change the image's Node entrypoint.
  • Data volume: keep the existing node data mount (default /var/lib/pg-node). Do not delete the volume or its xray-core directory to clean up. The old external core can stay unused; data and certificates live in that same volume.
  • Do not run the installer's core-update command after this change (default install: pg-node core-update; a custom --name changes the command). That command would write the external XRAY_EXECUTABLE_PATH again and select the upstream external core instead of the image's baked binary.

After recreating the container, confirm the effective value with the verification command below. Do not paste the full docker inspect or full docker compose config output anywhere public: those can expose secrets.

4Change the image and preserve the rest of the service

In the node service block, replace the entire existing image: value with this line. The executable-path correction in step 3 is the only environment edit:

image: ghcr.io/chownyourlife/pasarguard-node-custom-xray@sha256:bb09c94de5c448c1397634808f4158166a83ad1df80b0c180183d3cedf815f3f

Preserve the service's other environment values, TLS certificate and key paths, existing data mount, network_mode, cap_add, sysctls, ports, resources, and Node entrypoint. Do not edit the API key. Do not add volumes or environment variables other than the required XRAY_EXECUTABLE_PATH. Keep the data mount in place; on the default installer it is /var/lib/pg-node. If the image value is defined through an interpolated variable, change only the value used by this service and do not repurpose a variable shared by other services.

Do not use latest or the sha-5355... tag for this cutover. Both can be moved. The digest above is the pin. The image swap alone is not sufficient on a host whose environment still points at the external core; that is why step 3 is mandatory.

5Validate and pull without restarting the node

docker compose config --quiet
docker compose config --images
docker compose pull "$SERVICE"

config --quiet validates the Compose file and exits nonzero on syntax or interpolation problems. config --images prints the resolved image reference; confirm it is the digest above. The pull only downloads the image; the old node keeps running.

Optional platform check after the pull:

docker image inspect --format '{{.Os}}/{{.Architecture}}' "ghcr.io/chownyourlife/pasarguard-node-custom-xray@sha256:bb09c94de5c448c1397634808f4158166a83ad1df80b0c180183d3cedf815f3f"

The result should be linux/amd64 or linux/arm64 matching the host. If validation or pull fails, stop here; the old container has not been recreated and data has not been touched. Fix the issue or restore the backup before continuing.

6Recreate only the canary node

Active Xray sessions on this node will be interrupted, and the panel may briefly show the node disconnected. This is not a zero-downtime upgrade. Do this on one canary server first.

docker compose up -d --no-deps "$SERVICE"
docker compose ps "$SERVICE"

--no-deps keeps Compose from touching other services in the project. Run this with the same existing project and file flags as before; a different directory or project name can create a second stack. Compose normally recreates the container because the image digest and environment changed; if it says the container is already up to date, add --force-recreate to the same command. That recreates the container without deleting volumes. Do not use docker compose down, down -v, --remove-orphans, or volume-deletion commands. The image change does not remove or migrate the node's data directory.

Verify the canary before any rollout

docker compose ps "$SERVICE"
docker compose logs --tail=100 "$SERVICE"
docker compose exec "$SERVICE" printenv XRAY_EXECUTABLE_PATH
docker compose exec "$SERVICE" /usr/local/bin/xray version

CID=$(docker compose ps -q "$SERVICE")
docker inspect --format 'image_ref={{.Config.Image}} image_id={{.Image}}' "$CID"
  • Container state: it is running and is not in a restart loop.
  • Effective executable path: printenv XRAY_EXECUTABLE_PATH prints exactly /usr/local/bin/xray. If it prints a path under /var/lib/pg-node or another external location, the env correction did not take effect; fix it before testing further.
  • Baked core: the xray version output contains the full commit c8768463568d9655a67228531d4ed2690ee49dd7. If the path check or version check fails, check for a host binary override and confirm the running image reference from the last command. A stale XRAY_EXECUTABLE_PATH is the first thing to rule out.
  • Logs: no fatal errors, repeated restarts, authentication failures, or certificate errors. A log tail that simply ends without a fatal line is not by itself proof of health.
  • Panel: the node shows connected and healthy in the panel after startup.
  • Real client traffic: connect a real client through an existing inbound on this node and pass normal traffic. Confirm the node handles it and, if the panel exposes accounting or online status for that node, that it updates. Do not stop at docker compose ps or a TCP port check.

Rollback triggers: wrong XRAY_EXECUTABLE_PATH, missing fork commit, panel disconnect, client failure, TLS or authentication errors, container restart loop, or new fatal/error log lines. Roll back first, then diagnose. Do not keep restarting a live node that failed the canary.

Only after this canary passes should you continue. If the panel exposes a reported core version, verify it there as well; otherwise rely on the xray version exec check plus real client traffic.

Rollout and rollback

Roll out one server at a time

After the canary has passed and been observed for a meaningful period under representative traffic, repeat the same digest change and executable-path correction on the next server. Back up each server's Compose file and env file, record its previous image ID, pull the same digest, and verify panel connection plus a real client before moving on.

  • Do not restart all nodes at once; that takes every node offline simultaneously.
  • Do not use latest as the rollout target, even after the canary. Use the same digest on every host.
  • Keep each server's backups, env backup, and local pg-node-rollback:<timestamp> tag until the rollout is accepted.
  • Do not change API keys, certificate files, panel node records, data mounts, or host capability/routing settings as part of the rollout.
  • Do not run the installer's core-update command (default: pg-node core-update) on a node using this image. It re-points XRAY_EXECUTABLE_PATH at the external core.
  • Use the same existing Compose project and file flags on each host; do not create a second stack while intending to update the first.

Rollback a canary or a node

Restore every file you changed, including the Compose file, any env file where you changed XRAY_EXECUTABLE_PATH, and any wrapper or systemd file you edited, then recreate only the node. This removes neither data nor volumes. Run it with the same existing project and file options.

cp -p -- "$COMPOSE_PATH.bak.$STAMP" "$COMPOSE_PATH"

# If you edited an env file in step 3:
cp -p -- "$ENV_FILE.bak.$STAMP" "$ENV_FILE"

docker compose config --quiet
docker compose up -d --no-deps --force-recreate "$SERVICE"

docker compose ps "$SERVICE"
docker compose logs --tail=100 "$SERVICE"

Restoring the env backup also restores the previous XRAY_EXECUTABLE_PATH, which is appropriate for the previous image and environment. Then confirm the panel connection and test a real client again. If the previous image reference is no longer available locally, or the previous original tag may have moved, use the locally preserved rollback tag from step 2. STAMP is a non-exported shell variable, so Compose interpolation cannot see it; do not put the literal pg-node-rollback:$STAMP in the Compose file. Print the resolved tag in the same shell:

printf 'pg-node-rollback:%s\n' "$STAMP"

Copy the actual output (for example, pg-node-rollback:20261023T120000Z) as the node service's complete image: value, change nothing else, run the same recreation command, and verify. That tag points at the exact previous image ID and was not pushed to a registry, so pinning it guarantees the same previous bytes even if the original tag has since been overwritten locally or moved in the registry. The env restore above still applies, so the previous image also runs with its previous environment.

Never run docker compose down -v, delete the node data directory (default /var/lib/pg-node) or its xray-core directory, remove certificate files, or delete the node's API key as part of a rollback. Those actions can destroy data or break the panel connection and are not required by this image change.

If the failure was caused by an incompatible panel version, rollback returns the node to its previous image and environment, but the panel compatibility issue still needs a separate, planned fix. Do not use repeated production restarts as the diagnosis method.

Fresh-server prerequisites

This is deliberately not a complete install guide. A fresh node needs panel-side setup, a working API key, TLS certificates, data paths, and firewall/network configuration that the image does not create for you. Start from the official Node installation documentation (the guide targets Node v0.5.5) and the upstream Compose reference, then use this image in the node service.

  1. Install a current Docker Engine and Compose v2 plugin on a supported linux/amd64 or linux/arm64 host, and permit outbound HTTPS to ghcr.io.
  2. Use a compatible panel (v5.4.1 or v5.5.0; v5.5.0 is required for routing hot reload and Xray WireGuard inbounds according to the Node release notes). Create the node in the panel and provision its API key and TLS certificate/key following the official instructions.
  3. Follow the official Node setup for the data directory, TLS paths, network mode, port, and protocol. The upstream installer conventionally uses project pg-node, /opt/pg-node/docker-compose.yml, and /opt/pg-node/.env; a custom --name or APP_DIR changes those paths. This image does not generate or renew certificates, generate or register a node API key, open firewall ports, or download or refresh geodata at startup.
  4. Use the upstream Compose file and environment example, fill in host-specific values and real credentials locally, and set the node service's image to the digest above. Set XRAY_EXECUTABLE_PATH=/usr/local/bin/xray in the actual service environment, and leave the other service settings from the upstream file intact. Do not copy a made-up Compose file with placeholder credentials from this repository.
  5. If you used the installer's core-update command (default: pg-node core-update) for any reason, it will have written an external-core path into the env file. Change only that value back to /usr/local/bin/xray; do not delete the data volume or its xray-core directory. Avoid that command on a node that should use this image's baked core.
  6. Start one node, verify the effective XRAY_EXECUTABLE_PATH, panel connection, and a real client, then follow the same verification and canary approach. The rollback path is less relevant on a brand-new server, but keep the working upstream configuration before the image change.

Compatibility and behavior

  • Panel: Node v0.5.5 explicitly lists panel v5.4.1 and v5.5.0. Versions older than v5.4.1 are unverified by this project. Routing hot reload and Xray WireGuard inbounds need panel v5.5.0; do not enable newly unsupported features during this cutover.
  • Node version: the base is the official Node v0.5.5 image pinned by digest. This is not a newer or older Node release.
  • Core behavior: only the Xray binary is replaced. The Node application, its entrypoint, packages, and geodata path are inherited from the base image. There is no application-code change in this image.
  • Runtime downloads: the image adds no startup downloads. Geodata and packages are whatever the pinned base image contains; updating the base is a separate rebuild decision.
  • Credentials and data: replacing the image does not rewrite the API key, TLS files, other environment values, or node data. The one required environment correction is XRAY_EXECUTABLE_PATH=/usr/local/bin/xray; preserve everything else and keep the panel entry matching.
  • External core updates: do not use the upstream installer's core-update flow to update this image's core. It writes an external-core XRAY_EXECUTABLE_PATH and would bypass the baked binary. Build and publish a new image instead.
  • Capabilities and routing: preserve existing host capabilities and routing only. The image does not add WireGuard permissions or configure host sysctls.
  • Support scope: this is an unofficial custom image. The upstream Node and Xray projects are separate; this deployment guide does not imply upstream support for the fork.

Maintenance and builds

When the image rebuilds

  • A push to main rebuilds only when it changes Dockerfile, .dockerignore, scripts/**, or .github/workflows/build.yml. Documentation-only commits do not rebuild the image or move latest.
  • The workflow can also be started manually with workflow_dispatch.
  • Builds run natively on Ubuntu 24.04 amd64 and arm64 runners; smoke tests run before publication. Publication uses the workflow's GITHUB_TOKEN only.
  • A new build normally produces a new digest. Read the digest from the workflow summary; never assume latest or a commit tag still points at the digest in this guide. Update deployment pins only after the new image passes smoke and a canary.

Updating the custom Xray core

Do not use the installer's core-update command (default: pg-node core-update) to update this image. It writes XRAY_EXECUTABLE_PATH to an external core under the data directory; running that flow would bypass the baked binary and defeat this image. Update the pinned source in the Dockerfile, publish a new digest, and roll it out with the same canary process. Do not delete the node data directory (default /var/lib/pg-node) or its xray-core directory as part of that work.

  1. Replace the full commit in the Dockerfile source URL and in the -X github.com/xtls/xray-core/core.build= build metadata.
  2. Replace the source archive's SHA-256 checksum.
  3. Update the image labels that record the Xray source and commit.
  4. Update CORE_COMMIT in scripts/smoke.sh so the smoke test checks the new version.
  5. If the Node base changes, review the base digest, the upstream compatibility statement, and the NODE_COMMIT used for the smoke test's gRPC schema. Then run CI and canary the result.

The builder image, Node base image, and GitHub Action pins are deliberate. Review any pin change as a supply-chain change rather than routinely replacing them. The image has no runtime download step, so refreshing geodata or the core requires a rebuild, not a restart with a new download.
